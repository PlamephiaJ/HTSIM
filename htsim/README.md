# Overview

UEC htsim is based on the open source htsim Network simulator, extended with support for custom network topologies including Fat Tree, Dragonfly, and SlimFly.

## htsim Network Simulator

htsim is a high-performance discrete event simulator, inspired by ns2, but much faster, primarily intended to examine congestion control algorithm behaviour.  It was originally written by [Mark Handley](http://www0.cs.ucl.ac.uk/staff/M.Handley/) to allow [Damon Wishik](https://www.cl.cam.ac.uk/~djw1005/) to examine TCP stability issues when large numbers of flows are multiplexed.  It was extended by [Costin Raiciu](http://nets.cs.pub.ro/~costin/) to examine [Multipath TCP performance](http://nets.cs.pub.ro/~costin/files/mptcp-nsdi.pdf) during the MPTCP standardization process, and models of datacentre networks were added to [examine multipath transport](http://nets.cs.pub.ro/~costin/files/mptcp_dc_sigcomm.pdf) in a variety of datacentre topologies.  [NDP](http://nets.cs.pub.ro/~costin/files/ndp.pdf) was developed using htsim, and simple models of DCTCP, DCQCN were added for comparison.  Later htsim was adopted by Correct Networks (now part of Broadcom) to develop [EQDS](http://nets.cs.pub.ro/~costin/files/eqds.pdf), and switch models were improved to allow a variety of forwarding methods.  Support for a simple RoCE model, PFC, Swift and HPCC were added.

# Getting Started

htsim is written in C++, and has no major dependencies.  
It should compile and run with g++ or clang on MacOS or Linux.  

To get started with running experiments, take a look in the `htsim/sim/datacenter` directory where there are some examples.  
These examples generally require bash, python3 and gnuplot.


## Building the project

Install the Python requirements by running:

```bash
pip install -r requirements.txt
```

Then compile the project from the `sim/` folder by running

```bash
cmake -S . -B build # To configure the cmake project
cmake --build build --parallel # To build the project
```

## Run Validations

From the `sim/datacenter/validation` folder, run:

```bash
python validate_all.py --config_json_file example_validate.json > out.txt
```

Consider modifying the JSON file for more details.

The results will be saved in `sim/datacenter/validation/experiments`. There, each folder will contain a summary plot and a `tmp` folder where more details are stored.

Note that running this can take a long time depending on the chosen configuration.


The commit check validation suite is implemented in `sim/datacenter/commit_check.sh`.
By default, it runs a set of tests at 100Gbps speeds.

Validation workload files with different speeds and configurations can be generated by using the `sim/datacenter/generate_permutation_experiments.py` script:

```bash
python3 generate_permutation_experiments.py 800 NSCC > nscc_800gbps_test.txt
```

# Run Custom Scenarios

The UEC simulation binary is called `htsim_uec` and is located in `sim/datacenter/htsim_uec`.
To run a custom setup, a traffic/connection matrix must be provided.
Examples can be found in `sim/datacenter/connection_matrices`.

You can run a single network connection using UEC CMS as follows:

```bash
./htsim_uec -tm connection_matrices/one.cm
```

The output consists of two major parts: the configuration and setup section, and the runtime section.
The first part of the output shows the configured/derived/default parameter settings and values used by htsim.
It is important to verify that all the parameters are indeed accepted as expected when using custom configurations.
The runtime section starts with the `Starting simulation` line and ends with a packet summary. Per-flow completion records are written to `output_metrics/flowsInfo.csv`.

```
Starting simulation
.Done
New: 490 Rtx: 0 RTS: 0 Bounced: 0 ACKs: 124 NACKs: 0 Pulls: 0 sleek_pkts: 0
```

The last line shows a summary of the run, starting with the total number of packets sent, retransmissions, control messages, ACKs, etc. To restore verbose flow and trigger traces in stdout, set `HTSIM_TRACE_FLOW_COMPLETIONS=1` and/or `HTSIM_TRACE_TRIGGERS=1`.

To get more details, the `-debug` flag increases the output and shows more details on the active congestion control mechanism.


A second important, but optional parameter is the topology specification.
The simulator supports three network topologies:

### Fat Tree (default)

Fat tree topologies are the default and most mature topology. If no topology parameters are provided, htsim creates a 3-tier fat tree with 12µs RTT. Custom fat tree topologies can be specified via topology files.

Binary: `htsim_uec`

```bash
./htsim_uec -tm connection_matrices/perm_32n_32c_2MB.cm -topo topologies/leaf_spine_tiny.topo
```

### Dragonfly

Dragonfly topologies use a two-level direct-connect structure organized in groups. Pre-generated topology assets are provided in `topologies/dragonfly/` (e.g., `p3a6h3` for p=3 hosts/switch, a=6 switches/group, h=3 global links/switch).

Binary: `htsim_uec_df`

Supported routing strategies: `MINIMAL`, `VALIANT`, `UGAL_L`, `SOURCE`

Dragonfly accepts `-seed <uint32>` (global simulator RNG, default `13`) and
`-routing_seed <uint32>` (each Dragonfly switch's Valiant/UGAL candidate RNG,
default `33`). Set both when varying source-UGAL or native switch routing seeds.
Seeds initialize before topology construction; the routing algorithm and its
cost comparison are unchanged. `output_metrics/randomSeeds.csv` records both
executed values. Omitting these flags preserves the previous 13/33 defaults.

```bash
./htsim_uec_df -basepath topologies/dragonfly/p3a6h3 -tm traffic.tm -routing MINIMAL -q 88
```

For `SOURCE` routing, host-level routing tables are loaded automatically from the `host_table/` subdirectory within the topology path.

GOAL-driven Dragonfly runs pass each flow through the messagelet runtime. By default, the
messagelet size is the complete parent flow and every messagelet uses the minimum source
route. Pass a unified JSON configuration with
`-messagelet_config messagelet_configs/default.json`. The current schema is:

```json
{
  "schema_version": 1,
  "runtime": {"mode": "label", "granularity": "flow"},
  "messagelet": {"size_bytes": 0},
  "routing": {"default": "minimum", "network_decision": "none"},
  "logging": {"trace_decisions": false}
}
```

`runtime.mode` selects whether the runtime labels packets:

- `label` (default): choose and freeze routes at the configured granularity.
- `transparent`: keep GOAL submission/completion handling and use the original
  UEC sender, retransmission and receiver-control paths. The runtime does not
  call a network decision policy, assign SOURCE routes, or cache packet labels.
  Switches choose routes when packets arrive, including retransmissions.

To use native HTSim UGAL-L switch decisions, save this configuration and run
`htsim_uec_df -basepath ... -goal ... -routing UGAL_L -messagelet_config ...`:

```json
{
  "runtime": {"mode": "transparent"},
  "routing": {"network_decision": "none"}
}
```

Transparent mode also supports `-routing MINIMAL` and `-routing VALIANT`.
It rejects `-routing SOURCE`, static `-routing_config`, and runtime decision
policies such as `routing.network_decision="ugal_l"`. Granularity settings
remain configured but do not group or label packets while transparent mode is
active. Decision tracing consequently produces no `Messagelet route` entries;
use `HTSIM_TRACE_PACKET_HOPS=1` to inspect actual switch forwarding.
Select the mode before submitting flows; it is fixed for that simulation.
Transport entropy is still generated by native UEC, as it is without the
messagelet routing hook, and native switch routing ignores that entropy.

`runtime.granularity` explicitly selects the routing unit, independently of the
network decision policy, when `runtime.mode="label"`:

| Granularity | Decision boundary | `messagelet.size_bytes` |
| --- | --- | --- |
| `flow` (default) | Once per complete parent flow | Omit or set to `0` |
| `messagelet` | After the current group reaches its byte budget | Required, greater than `0` |
| `packet` | Once per new data packet | Omit or set to `0` |

Messagelet byte budgets count full transmitted packet bytes, including headers;
splits occur at packet boundaries and can exceed the budget by part of one
packet. Flow mode always keeps the complete flow together, including its packet
headers. Packet mode treats each new data packet as a one-packet messagelet;
retransmissions retain their original packet's label at every granularity. Control
packets reuse the current routing unit and do not advance its index.

For existing schema-1 configurations that omit `runtime.granularity`, a positive
`messagelet.size_bytes` still selects messagelet mode, and zero or omitted size
selects flow mode. Explicit modes reject conflicting sizes. Decision traces
include `Granularity`, the path ID and the selected route; in packet mode `Size`
is the configured maximum data packet size, including headers.

To select routes from live network load before labelling each messagelet, set
`routing.network_decision` to `"ugal_l"` and run with `-routing SOURCE -goal ...`:

```json
{
  "schema_version": 1,
  "runtime": {"granularity": "messagelet"},
  "messagelet": {"size_bytes": 8192},
  "routing": {"default": "minimum", "network_decision": "ugal_l"},
  "logging": {"trace_decisions": true}
}
```

For packet-level decisions in the runtime, use `"runtime": {"granularity": "packet"}`
and omit `messagelet.size_bytes` (or set it to zero). Forwarding still uses
`-routing SOURCE`: the packet's label is fixed throughout its network traversal.

The runtime calls `NetworkDecision::decide()` once, immediately before a messagelet
receives its path ID. All packets in that messagelet, including retransmissions,
retain the selected label. Each later messagelet observes current queue sizes.
The existing control-packet hook can start a messagelet decision before its first
data packet. Flow granularity keeps the complete flow in one messagelet.

`UgalLNetworkDecision` reuses `DragonflySwitch::ugalDecision()`, which also serves
HTSim's packet-level `UGAL_L` routing. It preserves the existing Valiant candidate
sampling, per-switch seed-33 RNG, hop-count walks, and local egress queue byte
counts. A Valiant candidate wins only when `q_min * h_min > q_val * h_val`;
ties choose minimal. Matching first hops bypass the comparison, and hosts on
the same switch are delivered locally. The selected candidate's first two hops
are encoded as a SOURCE path, including the sampled second hop used during the
Valiant hop-count walk. Subsequent forwarding follows that fixed path with no
further UGAL decisions. This applies HTSim's decision at messagelet boundaries;
the `-routing UGAL_L` mode continues making decisions at each packet hop.

The default `"none"` preserves static/default routing. A network decision policy
and `-routing_config` are mutually exclusive. To implement another policy, derive
from `NetworkDecision` and install it with
`MessageletRuntime::setNetworkDecision(std::unique_ptr<NetworkDecision>)`; register
it in the configuration factory/validator if JSON selection is needed. Replacing
the policy affects future messagelets. `setMessageletRoute()` can override a
future messagelet; modifying a route after its first lookup raises an error.
Decision traces include the policy, selected path, and queue/hop counts when a
comparison occurs.

C++ callers can inspect `MessageletRuntime::granularity(source)` and configure a
registered flow with `setGranularity(source, Granularity::Flow)`,
`setGranularity(source, Granularity::Messagelet, 8192)`, or
`setGranularity(source, Granularity::Packet)`. `setMessageletSize(source, bytes)`
selects messagelet mode. Per-flow changes take effect at the next routing-unit
boundary; the active unit keeps its cached mode, size and label. A flow unit
ends only when that flow finishes, so select its mode before its first lookup
when splitting the current flow is required.

Build and run the standalone network decision tests without fetching GoogleTest:

```bash
cmake -S htsim/sim -B htsim/sim/build -DENABLE_NETWORK_DECISION_TESTS=ON
cmake --build htsim/sim/build --target htsim_uec_df network_decision_test --parallel 4
ctest --test-dir htsim/sim/build -R network_decision_test --output-on-failure
python3 -m unittest discover -s experiments/common -p 'test_network_decision.py'
```

GOAL ranks map to HTSIM hosts in their existing sequential order by default. To place ranks
explicitly, pass `-rank_placement path/to/placement.json`. Each entry names the GOAL rank
and its Dragonfly endpoint using group-local switch and host indices:

```json
{
  "schema_version": 1,
  "placements": [
    {"rank": 0, "group": 0, "switch": 0, "host": 0},
    {"rank": 1, "group": 1, "switch": 0, "host": 0}
  ]
}
```

The placement must contain every workload rank exactly once. Dragonfly endpoints must be
unique and within the selected topology. Omitting `-rank_placement` preserves the sequential
mapping.

#### Spritz Source Routing

The Dragonfly and SlimFly binaries accept the Spritz artifact-style source load balancer flags when `-routing SOURCE` is selected:

- `-LB ECMP`: deterministic source-path hashing.
- `-LB OPS`: oblivious path selection; use `-flow-weight-scaling 0` for uniform OPS and a positive value such as `3` for latency-weighted OPS.
- `-LB FLICR`: Flicr-style adaptive source-path selection.
- `-LB FLOW_V1`: Spritz-Scout.
- `-LB FLOW_V2`: Spritz-Spray.

The Spritz knobs from the artifact scripts are also supported: `-flow-explore-threshold`, `-flow-ecn-threshold`, `-flow-weight-scaling`, `-flow-sort-insert`, `-flow-small-flows-bias`, `-flow-small-flows-threshold`, and `-flow-small-flows-weight`. The `-CC` aliases used by the Spritz artifact are accepted; `SMARTT_ECN` maps onto this tree's NSCC/SMaRTT-compatible congestion-control path.

Example Spritz-Spray run on the Dragonfly workload used by the paper scripts:

```bash
cd htsim/sim/datacenter
./htsim_uec_df \
  -basepath ./topologies/dragonfly/p4a8h4 \
  -tm ./experiments/df/p4a8h4/permutation_global_4MiB.cm \
  -p 4 \
  -routing SOURCE \
  -CC SMARTT_ECN \
  -LB FLOW_V2 \
  -flow-explore-threshold 44 \
  -flow-ecn-threshold 8 \
  -flow-weight-scaling 3 \
  -flow-sort-insert 1 \
  -flow-small-flows-bias 1 \
  -flow-small-flows-threshold 524288 \
  -flow-small-flows-weight 100.0
```

Each run exports CSV metrics in `output_metrics/`, including `flowsInfo.csv`, `packetInfo.csv`, and `globalInfo.csv`.
By default, UEC flow completion and trigger traces are not printed to stdout; set `HTSIM_TRACE_FLOW_COMPLETIONS=1` or `HTSIM_TRACE_TRIGGERS=1` when debugging old log-parsing workflows.

To generate custom Dragonfly topology assets (`dragonfly.topo`, `dragonfly.adjlist`, `host_table/`) for any `(p,a,h)`, use:

```bash
python sim/datacenter/topologies/dragonfly/generate_dragonfly_assets.py -p <p> -a <a> -H <h> --out sim/datacenter/topologies/dragonfly/p${p}a${a}h${h}
```

Example for 4 hosts (`p2a1h1`):

```bash
python sim/datacenter/topologies/dragonfly/generate_dragonfly_assets.py -p 2 -a 1 -H 1 --out sim/datacenter/topologies/dragonfly/p2a1h1
```

### Traffic Matrix Format

All topologies use the same traffic matrix format:

```
Nodes <N>
Connections <M>
<src>-><dst> start <picoseconds> size <bytes>
```

For example, a single 1 MiB flow starting at time 0 in a 342-host network:

```
Nodes 342
Connections 1
0->341 start 0 size 1048576
```

The `datacenter/topologies` folder contains a set of examples.

# Entry switch messagelet routing

Dragonfly GOAL runs support `SOURCE` (the default host routing mode) and
`ENTRY_SWITCH`. Select the latter in both the simulator and messagelet config:

```json
{
  "runtime": {
    "mode": "label",
    "routing_mode": "ENTRY_SWITCH",
    "dag_id": 0,
    "granularity": "messagelet"
  },
  "messagelet": {"size_bytes": 16640},
  "routing": {
    "network_decision": "commitment_aware_ugal",
    "commitment_alpha": 1.0
  },
  "logging": {"trace_decisions": true}
}
```

```bash
htsim/sim/build/datacenter/htsim_uec_df \
  -basepath /path/to/topology -goal /path/to/workload.bin \
  -routing ENTRY_SWITCH -messagelet_config /path/to/messagelet.json
```

The runtime automatically reads the adjacent `workload.meta.json`. Use
`-flow_metadata /path/to/workload.meta.json` for a different location. Metadata
must map every GOAL `(source rank, send task ID)` to its DAG-global flow ID;
ENTRY_SWITCH requires this mapping and validates endpoints, tags, and sizes.
`runtime.dag_id` defaults to zero. Static `-routing_config` labels and transparent
runtime mode cannot be combined with ENTRY_SWITCH.

The host splits the flow and attaches the same key
`(dag_id, flow_id, messagelet_idx)` and metadata `(mlet_size, total_mlet)` to every
data packet in a messagelet, including retransmissions. Indices start at zero.
It leaves path IDs unassigned. As in SOURCE mode, `messagelet.size_bytes` is a
wire-byte segmentation threshold, rounded up to whole packets. Metadata
`mlet_size` is the **actual original payload bytes** in this messagelet; the last
messagelet can be smaller. `total_mlet` counts the resulting messagelets in the
flow. Flow and packet granularities are also supported. Once ENTRY_SWITCH
metadata has been issued, segmentation cannot be changed through the C++ hooks.

On the first arrival of any packet with a new key, the source host's directly
connected switch selects and caches its path, then commits `mlet_size` to its
group's GRA before the packet enters the switch delay pipe or an egress queue.
Further packets and retransmissions reuse that path without recommitting.
This preserves `Q + alpha * R`: Q counts queued wire bytes and R counts committed
original payload that has not yet entered its selected global corridor. A drop
or trim before intact admission leaves those bytes in R; the first intact
admission consumes them exactly once. Intra-group traffic has no global corridor
commitment. Control packets follow minimum routes without payload commitments.

`routing.network_decision` also accepts `ugal_l` and `none` (minimum routes).
With tracing enabled, `entry_decisions.csv` records switch decisions and the
source-provided key/metadata; `gra_events.csv` records commitments and unique
admissions, including DAG and global flow IDs. Switch and host modes must agree.
To use host decisions, set `-routing SOURCE` and
`runtime.routing_mode: "SOURCE"` (or omit that field).

Build and validate:

```bash

cmake --build htsim/sim/build --target htsim_uec_df network_decision_test soft_claim_test gra_static_graph_test gra_execution_progress_test -j 4

```

### Optional DAG-aware Soft Claim

Soft Claim is disabled by default. For `ENTRY_SWITCH` with
`routing.network_decision: "commitment_aware_ugal"`, add:

```json
"routing": {
  "network_decision": "commitment_aware_ugal",
  "commitment_alpha": 1.0,
  "soft_claim": {"enabled": true, "policy": "dag_priority", "beta": 1.0}
}
```

A complete example is `sim/datacenter/messagelet_configs/soft_claim.json`.
`routing.soft_claim.beta` controls claim pressure and defaults to the configured
`routing.commitment_alpha` when omitted. Both must be finite and nonnegative.
Set beta to zero to ignore claim pressure while keeping READY/claim tracking.

Set `enabled` to `false`, or omit `soft_claim`, to retain the existing routing
and accounting behavior. Enabling it with SOURCE, transparent mode or another
network decision is rejected. Flow, messagelet and packet granularities work.

At GOAL SEND submission (after its dependencies and send gate are satisfied),
the runtime reports the first messagelet READY, with actual payload bytes and
DAG identity. When all original data in that messagelet has been handed to the
sender, the next messagelet becomes READY. This is a logical sending eligibility
signal, not a guarantee of immediate NIC/credit availability. Unsubmitted DAG
tasks and the rest of a flow's unsent suffix do not receive claims. No packets
are delayed by this mechanism.

Each GRA predicts a preferred outgoing global corridor for each pending READY
messagelet using UGAL's sampled candidates, hop weights and **only** `Q + alpha * R`.
Prediction previews the source switch's current routing RNG state without
advancing it. Predictions refresh on READY, decision, cancellation, and just
before a routing query, so they use current Q/R. They do not fix the actual path
or guarantee the same future Valiant sample. Intra-group traffic has no claim.
The highest `dTable()[(dag_id, flow_id)]` on each preferred corridor owns its
single claim. Equal priorities use key order for deterministic ownership and
never penalize each other. Each messagelet can own at most one claim.

At the first packet's entry decision, the pressure for each candidate corridor is
`Q + alpha * R + beta * S`, followed by the existing hop-weighted UGAL comparison.
`S` is the owner's **actual payload bytes**, counted once and scaled by beta,
only if the owner has strictly greater D than the requester. Self claims are
ignored. Missing READY or unknown DAG identity gives `S = 0`. A high-priority
owner can still choose Valiant when actual network costs favor it.

Commit removes that messagelet's pending demand and recomputes claims using the
updated R. Remaining packets and retransmissions retain the cached path and
the existing first-admission accounting. Soft Claims never contribute to R.
With `logging.trace_decisions`, `gra_soft_claims.csv` records post-event pending
counts and claim snapshots; `entry_decisions.csv` adds `soft_claim_min_bytes`
and `soft_claim_val_bytes` to `policy_state`, alongside beta and total compared pressures.

With the same trace switch, `gra_pending_preferences.csv` records **every pending
messagelet** after each preference refresh (READY, routed, cancel, and the
refresh immediately before a global routing decision). Rows include source and
destination hosts, actual payload, D priority, preferred corridor, its current
Claim owner/priority/payload, and `claim_status`:

| Status | Meaning |
| --- | --- |
| `owner` | This pending messagelet owns the Claim on its preferred corridor. |
| `higher_priority_owner` | Another messagelet with greater D owns it. |
| `equal_priority_tiebreak` | Another equal-D messagelet won the deterministic key tie break. |
| `no_corridor` | The preference oracle returned no global corridor. |
| `unclaimed` | The preferred corridor has no Claim. |
| `preference_unavailable` / `policy_not_selected` | An alternative strategy did not supply a preference or selected an owner for another policy-specific reason. |
| `empty` | Snapshot marker: no pending messagelets remain. |

Use `(group, snapshot_id)` to collect a full snapshot; `pending_count` gives its
size (zero uses one empty marker row). `refresh_reason` and the trigger's DAG,
flow and messagelet IDs identify the event. `entry_decisions.csv`'s
`policy_state.soft_claim_snapshot_id` references the exact pre-decision snapshot,
including refreshes that changed preferences without changing the Q/R version.

For compared global candidates, `policy_state` also records
`soft_claim_min_reason` / `soft_claim_val_reason`, the beta-scaled
`soft_claim_min_pressure` / `soft_claim_val_pressure`, requester D, and each
existing owner's DAG/flow/messagelet identity, D and original payload:

| Reason | Meaning |
| --- | --- |
| `applied` | A strictly higher-priority owner's demand contributes pressure. |
| `missing_ready` | Requester is absent from pending; baseline fallback. |
| `missing_identity` | Caller did not supply a messagelet key. |
| `no_claim` | No owner exists on this candidate corridor. |
| `self_claim` | Requester owns this Claim. |
| `equal_priority` | Owner and requester have equal D. |
| `lower_priority` | Owner has lower D than the requester. |
| `beta_zero` | An eligible higher-priority Claim exists, but beta is zero. |

Missing READY takes precedence over corridor/priority exclusions. The existing
`soft_claim_*_bytes` fields remain **eligible unscaled bytes**, so they can be
positive with `beta_zero` while `soft_claim_*_pressure` is zero. An existing owner
is recorded even when ignored; absent-owner fields are omitted. When no candidate
comparison runs, no candidate pressure/reason is invented;
`soft_claim_evaluation` distinguishes `not_compared` from `intra_group` (and
`not_commitment_aware` for a directly installed alternative decision policy).
Alternative demand policies can provide their own diagnostic reason codes via
`RoutingDemandPolicy::observePressure()`; the default is `policy_defined`.
Disabled Soft Claim produces none of these additional demand logs. Preference
logging reuses the actual refresh results without rerunning the routing oracle.

The experiment is isolated in `routing_demand_policy.{h,cpp}`. The
`RoutingDemandPolicy` interface takes READY/remove events, a base-network
preference callback and pressure queries; it has no topology, packet, queue or
Commitment ownership. To try another strategy, implement this interface and
extend `makeRoutingDemandPolicy()` and config validation, or install one through
`GroupRoutingAgent::setDemandPolicy()` before READY reports. The GRA adapter
supplies D and network observations; runtime and transport hooks stay intact.
`MessageletRuntime::cancelMessageletReady()` (or GRA's `cancelReady()`) retracts
pre-routing demand and promotes the next owner. The existing GOAL scheduler has
no cancellation event; a future transport cancellation caller must invoke this
hook and stop the cancelled transmission itself. Replacing/disabling a policy
discards its pending soft state and leaves real commitments intact.

### GRA static computation graphs

Every GOAL-driven Dragonfly run snapshots the complete GOAL graph before the
scheduler issues any task. Each matched SEND/RECV pair becomes one logical
`COMM`, carrying its full payload bytes and DAG-global `flow_id`. Each local
compute task becomes a `COMP` whose nominal cost is its GOAL duration in ns.
Dependencies retain their release event (`START`, `RECEIVE_START`, or `FINISH`)
and target endpoint (`START` or `RECEIVE_START`). A SEND and its paired RECV
share one completion event, but their start events remain independent. Exact
duplicate typed edges are collapsed.
The graph and the following maps are computed once, then shared by all GRAs
through a `shared_ptr<const GraStaticGraph>`:

| Map | Key | Value |
| --- | --- | --- |
| `dTable()` | `(dag_index, flow_id)` | `uint64_t D_ns` |
| `structureTable()` | `(dag_index, flow_id)` | Collection of `(dag_index, flow_id, join_id, branch_id, tail_to_join_ns)` records |
| `joinTable()` | `(dag_index, join_id)` | `(dag_index, join_id, branch_count)` |

Initialization expands logical nodes into a weighted event DAG. A COMP has a
start-to-finish edge carrying its duration. A COMM has exactly one weighted
SEND-start-to-finish edge carrying its communication cost, plus a zero-cost
RECV-start-to-finish edge. Thus communication completion obeys
`finish = max(send_start + cost, receive_start)`: transfer can proceed before
RECV is posted. FINISH dependencies originate at completion; START dependencies
originate at the corresponding endpoint's start. Every dependency targets the
dependent task's start event and carries zero cost.

Reverse topological evaluation uses
`L(event) = max(edge_cost + L(successor_event))`, with zero at terminal events.
The D table stores `L(send_start)` for each COMM. For ordinary serial FINISH
chains this reduces to the original `w(v) + max(D(successor))` recurrence.
A START-released 1000 ns compute task overlaps a 100 ns COMM, yielding
`D = max(100, 1000) = 1000 ns`, rather than 1100 ns. If a START-only branch
dominates, the originating COMM's cost is not added to that parallel branch;
it is already represented by the separate transfer edge. Communication cost is exactly
`ceil(payload_bytes * 8 * 10^9 / global_link_speed_bps)` ns, using the global
link bandwidth from the topology settings and wide integer arithmetic. It
excludes packet headers, hop counts, queueing, and simulated completion times.

Every node with more than one distinct direct predecessor is a Join, including
COMM nodes and terminal compute tasks. This counts logical predecessor nodes
across both endpoint starts; multiple START/FINISH edges from one predecessor
form one branch. Internal lifecycle edges and dependencies between endpoints
of the same COMM do not create Join branches. Join IDs start at zero in logical
node order; branch IDs follow distinct direct predecessor order.
For each COMM, the structure map starts at its **completion** event and follows
event paths only until their first dependency entering a logical Join. The
tail is the longest weighted path to that entry, excluding the originating
COMM and the Join's own cost. START dependencies along intervening paths keep
their overlap semantics. Work released only by the originating COMM's START
is not downstream of its completion and does not enter its structure records.
A direct COMM-FINISH-to-Join dependency has tail zero. COMM nodes without a
downstream Join have an empty record collection.

Access the immutable graph and tables with
`topology.groupRoutingAgent(group).staticGraph()`. All messagelets of a flow
use the same `(dag_index, flow_id)` entry. The current GOAL loader installs one
DAG using `runtime.dag_id` as its index (default `0`); the static graph builder
also supports multiple DAGs. Reinitialization is rejected.

Flow identities come from workload metadata or static routing labels. If both
are supplied they must agree. Metadata's `recv_task` identifies the matching
receive task; older metadata may omit it when `(src, dst, tag)` uniquely
identifies the pair. Outside ENTRY_SWITCH mode, runs without either identity
file use `(source_rank << 32) | send_task_id` consistently for the static tables
and runtime messagelets. Ambiguous or unmatched endpoints, cycles in the
expanded event graph, and costs exceeding `uint64_t` are rejected at startup.
The logical node projection may contain a cycle while the event graph remains
acyclic: opposite SEND-START-to-RECV-start dependencies are valid. Opposite
SEND-FINISH-to-RECV-start dependencies still form a real completion deadlock
and are rejected. The model accounts for nominal causal dependencies; runtime
CPU/NIC contention, network queues, and measured timings remain outside these
static tables.

### GRA execution progress and Frontier

The static graph retains the original `(rank, task_offset)` index built by the
GOAL importer, including the SEND/RECV distinction, and the event predecessor
relations already constructed during initialization. These are graph lookup
indices; the D, structure, and Join tables remain immutable.

Host information follows `Host -> MessageletRuntime -> switch/GRA`.
`AtlahsDragonflyApi` is a thin scheduler adapter: communication submissions,
static graph initialization, and execution progress are forwarded to the
messagelet runtime. It owns no progress versions or GRA reporting logic.

Each rank delivers actual lifecycle transitions to
`MessageletRuntime::reportTaskProgress()` through that adapter. The scheduler's
first START/FINISH callbacks pass original task identities and actual times;
the runtime builds reports with `dag_index`, `rank`, `task_offset`, `event`,
`version`, and `event_time_ns`. Version numbers start at 1 and increase for every
report from that rank, across DAGs. Reports use scheduler nanoseconds and
original task identities; Hosts do not translate internal graph node IDs.
The runtime owns the per-rank sequence, resolves the source group from rank
placement and task NIC, delivers reports to GRA, and records optional traces.

SEND START confirms COMM START; RECV START confirms RECEIVE_START. COMP reports
confirm their corresponding START or FINISH. Matched message completion marks
both GOAL endpoints finished, but only the sender's FINISH report confirms
the shared logical COMM FINISH. The receiver's FINISH consumes its rank's
version without creating a second logical event. Merely issuing a send or
posting a receive never confirms communication completion.

Each GRA owns a separate `GraExecutionProgress`. Duplicate or already processed
versions are ignored. Reports beyond a version gap are buffered without
confirming their events; filling the gap processes the contiguous buffered
reports. Invalid task identities are rejected. Duplicate logical events retain
their first actual timestamp, and conflicting timestamps are rejected.
Receiving an event never implicitly confirms its missing prerequisites.

The current ground-truth model delivers each report immediately to the source
group and freely fans it out to all other GRAs. No synchronization messages,
delays, or global scheduler reads are modeled. Direct `gra.receiveProgress()`
calls update only that GRA, so independent partial views can also be tested.

Query the current view with:

```cpp
const auto& gra = topology.groupRoutingAgent(group);
const auto& observed = gra.executionProgress().confirmedEvents();
auto frontier = gra.frontier(dag_index);
```

An unconfirmed static event belongs to the Frontier exactly when all of its
direct predecessor events are confirmed. Roots are initially eligible.
Readiness never changes execution state: a ready COMP START needs an actual
START report before its FINISH can become eligible; COMM FINISH becomes
eligible after both endpoint starts but remains unconfirmed until completion
is reported. Nominal costs do not act as dynamic completion timers, including
for zero-duration tasks. The Frontier is recomputed on demand from retained
event relations and received observations, without a persistent Frontier table.
It does not affect routing or urgency calculations.

Set `HTSIM_TRACE_GRA_PROGRESS=1` to export `gra_progress_reports.csv`, containing
each Host report, its source group, the resulting confirmed-event count, and
that group's Frontier after delivery. Tracing is optional; normal progress
updates do not calculate or cache the Frontier.
